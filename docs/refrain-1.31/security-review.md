# Ревью безопасности сервера Refrain ИИ (server/) — черновик, дописывается

Статус: код `server/src/**`, `migrations/0001_init.sql`, `wrangler.toml`, `shared/refrain/*`, `shared/prompts/*` прочитан. Воспроизводящие тесты — в работе (см. «Не проверено»). Временных файлов в репозитории нет.

## Находки (от серьёзных к мелким)

### 1. ВЫСОКО — перебор кода входа параллельными запросами (обход «5 попыток»)
- `server/src/auth.ts:278-289` (`authVerify`): `SELECT attempts` → проверка → `UPDATE login_codes SET attempts = ?2` значением `row.attempts + 1`, посчитанным из прочитанной строки. Не атомарно.
- Сценарий: злоумышленник запрашивает код на чужую почту (`/v1/auth/start`, 3 в час), затем шлёт пачку из N параллельных `/v1/auth/verify` с разными кодами. Все читают `attempts = 0`, все пишут `attempts = 1`. За «5 попыток» проходит ~5×N догадок. Лимита по IP на `/verify` нет, PoW нет.
- Вес: захват аккаунта. Для почты владельца (OWNER_EMAIL) — группа `owner`: без дневного лимита и с обходом общего бюджета (`task.ts:326`, `bypass`), то есть неограниченный расход OpenAI.
- Исправление: атомарно `UPDATE login_codes SET attempts = attempts + 1 WHERE email = ?1 AND attempts < 5 AND expires_at > ?2 RETURNING attempts` **до** сравнения кода; нет строки — отказ. Плюс лимит `/verify` по IP и по почте (bump), запись `auth_fail` на каждый промах.

### 2. ВЫСОКО — то же для PIN и кода панели: блокировка «5 неверных PIN» обходится параллельностью
- `server/src/admin.ts:37-49` (`pinOk`): `fails = cfg.pinLock.fails + 1` из настроек, прочитанных в начале запроса; пишется абсолютное значение. Параллельные запросы все пишут `fails = 1`, порог 5 не достигается.
- `server/src/admin.ts:76-81`: код панели — проверка `row.attempts >= 5` до инкремента; `attempts + 1` атомарен, но проверка по устаревшему чтению → параллельный перебор.
- Нужен действующий токен панели (для `needPin`) или верный код панели (для входа по почте), поэтому вес ниже п.1, но требование «5 неверных PIN — закрыто на час» не выполняется.
- Исправление: счётчик неудач PIN — отдельная строка с атомарным `UPDATE … SET fails = fails + 1 … RETURNING`, проверка блокировки по результату; для кода — как в п.1.

### 3. ВЫСОКО — задача, брошенная клиентом, не списывается ни ученику, ни бюджету
- `server/src/counters.ts:136,216` — истёкший замок/резерв (3 мин) просто удаляется, без списания. `server/src/task.ts:337-343` — списание только после ответа OpenAI в том же обработчике, не в `ctx.waitUntil`.
- Сценарий: клиент шлёт `/v1/task` и обрывает соединение после отправки запроса в OpenAI. В Workers отключение клиента отменяет обработчик (кроме `waitUntil`), `settle` не выполняется: OpenAI тратит деньги, счётчик ученика и общий бюджет — нет; строки в `usage` тоже нет. Каждый аккаунт так может ~20 задач в час «бесплатно», лимиты дня/месяца не растут. Любой сбой Worker между `begin` и `settle` (лимит CPU, исключение) даёт тот же эффект.
- Частично ловит только сверка с Usage API (порог $0.5 и +25 % за окно 60 мин): ниже порога — до ~$12/сутки незаметно при месячном бюджете $20; выше — аварийная пауза и ложная «утечка ключа» (отказ в обслуживании, нужно менять ключ).
- В miniflare не воспроизводится (отмену по разрыву он не моделирует) — проверено трассировкой кода.
- Исправление: вызов OpenAI и `settle` выполнять внутри `ctx.waitUntil` (ответ ждёт тот же промис); истёкший резерв **списывать** в полном размере (а не удалять) и в DO ученика, и в бюджете; строку `usage` писать до вызова (с резервом) и обновлять после.

### 4. СРЕДНЕ — чужой аккаунт можно «выбить» и заблокировать, зная только id устройства
- `server/src/sign.ts:160-181`: баллы `token_unknown` (аккаунту +15), `time_skew` (устройству +5), `sig_invalid` (устройству +40) начисляются аккаунту/устройству из заголовка `x-refrain-device` **до** проверки подписи — то есть без доказательства владения ключом.
- Сценарий: 3 запроса с id устройства жертвы и мусорной подписью → устройство 120 баллов → уровень 2 (`guard/index.ts:112,126-136`): закрыты все сессии, устройство отвязано. Повтор в течение суток → блок аккаунта на 24 ч (`guard/index.ts:137-145`). Id устройства не секрет: ходит в заголовках, может попасть в журнал бага, а журнал бага уходит в открытый GitHub issue (п.8).
- Исправление: до успешной проверки подписи начислять баллы только IP; аккаунт/устройство — только после `verifyDevice` (или вовсе не за `sig_invalid`, а за `nonce_replay`, `refresh_reuse`).

### 5. СРЕДНЕ — блок обходится удалением аккаунта
- `server/src/me.ts:132-151` + `auth.ts:272-327`: заблокированный ученик (блок хранится в `accounts.blocked_until` и `blocks` по id аккаунта) входит заново (вход не проверяет блок), вызывает `DELETE /v1/account` (не проверяет блок) и регистрирует ту же почту — новый id, блока нет. Требование «разблокировка только из панели» нарушено. Заодно сбрасываются дневной/месячный счётчики (`wipe`).
- Исправление: при активном блоке отказывать в удалении (или держать блок по хэшу почты: таблица `blocked_emails(email_hash, until)`), проверять её при входе.

### 6. СРЕДНЕ — почтовые псевдонимы дают неограниченно аккаунтов
- `server/src/accounts.ts:31` (`normEmail` — только trim/lowercase), `auth.ts:209` (`+` разрешён). `name+1@gmail.com`, `n.ame@gmail.com` — разные аккаунты с одним ящиком; лимит «3 кода в час» — на каждый псевдоним. Каждый — «Новичок» 10 стр./день. Защищает только «волна регистраций» (которая сама обнуляет «Новичка» всем — отказ в обслуживании честным).
- Исправление: каноническая почта для лимитов и уникальности (срезать `+тег` у всех; точки — для gmail/googlemail).

### 7. СРЕДНЕ — лимиты по IP не работают для IPv6
- `server/src/http.ts:276-280`: ключ — весь адрес. У клиента IPv6 обычно /64 (2^64 адресов): лимит 10 кодов/час на IP, 20 багов/час, блок IP детектором — обходятся сменой адреса.
- Исправление: для IPv6 хэшировать префикс /64 (для лимитов и детектора).

### 8. СРЕДНЕ — в GitHub issue (открытый репозиторий) могут уйти ID и токены
- `server/src/bugs.ts:237-243` (`scrub`) убирает почты, пути и числа ≥7 цифр; не убирает `acc_…`, `dev_…`, `ses_…`, токены `v1.….…`, base64url-строки, IPv4/IPv6. `bugToGithub` (`bugs.ts:286-305`) публикует журнал как есть. Требование «без почты, ID» выполнено частично; id устройства из issue — вход для п.4.
- Исправление: вычищать `\b(acc|dev|ses)_[A-Za-z0-9_-]{8,}`, `v1\.[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+`, длинные base64url (`[A-Za-z0-9_-]{20,}`), IP-адреса.

### 9. СРЕДНЕ — «PIN, если бюджет больше чем вдвое» обходится шагами
- `server/src/admin.ts:130`: сравнение с текущим значением; 20 → 40 → 80 → … → 10000 за ~9 запросов без PIN. При `dayUsd = null` (по умолчанию) `Infinity * 2` — дневной бюджет вообще без PIN. `PUT /groups` (лимиты до 100000 или `null` = без лимита) и `accounts/:id/group` → `tester` — без PIN.
- Исправление: PIN, если новое значение больше **дефолта/подтверждённого PIN-ом** значения ×2 (хранить `budgetApprovedUsd`), и для любого повышения лимитов групп / `null`.

### 10. СРЕДНЕ — дешёвая аварийная пауза и блок целого ASN
- `server/src/guard/index.ts:243-247`: уровень 3 — 10 аккаунтов с уровнем 2 за 15 мин, причём считаются и `pending`, и строки «отзыв без блока» (`markLevel2`). Свои 10 аккаунтов (п.6) + по 3 запроса с неверной подписью = пауза для всех.
- `guard/index.ts:158-161`: 3 заблокированных IP в одном ASN → блок ASN (вход и задачи) для всех учеников этого оператора. Свои 3 IP у мобильного оператора — и сеть закрыта на 30 мин, можно повторять.
- Исправление: в `checkMass` считать только аккаунты старше N дней / с успешными задачами, без `pending`; блок ASN — только тревогой с кнопкой (или только для новых аккаунтов), не автоматически.

### 11. НИЗКО — резерв ученика не резервирует
- `server/src/counters.ts:163-175`: лимит ученика проверяется по уже списанному (`used >= limit`), `reserve` не используется. Перерасход — на одну задачу сверх лимита. Требование «резервирование максимальной стоимости» выполнено только для общего бюджета.

### 12. НИЗКО — потолок стоимости может быть ниже настоящей
- `shared/prompts/tasks.ts:273-276`: 2 знака на токен и 200 токенов на предмет/тему/указания (до 640 знаков). Текст из редких символов/эмодзи даёт >1 токена на знак → реальная цена больше резерва → бюджет можно превысить на величину одной пачки. Цены — константы `DEFAULT_PRICES`, не из конфига.

### 13. НИЗКО — прочее
- `server/src/auth.ts:388-409`, `me.ts:108-115`: перебор приглашений без лимита (31^8, практически не опасно, но нет сигнала детектору).
- `server/src/auth.ts:353-376`: два параллельных refresh одним токеном — оба успешны, второй токен первого «теряется» без признака кражи.
- `server/src/auth.ts:304-312`: лимит устройств обходится параллельными verify одним кодом.
- `server/src/tasks budgetAlerts` (`task.ts:399`) и `bump greedy` (`task.ts:380`): месяц/день по UTC, счётчики — по Москве.
- Удаление аккаунта (`me.ts`) оставляет маску почты в `blocks.label`, `alerts.who`; маска IP в `blocks.label`, `journal.target_id` и `alerts.who` хранится бессрочно (в миграции заявлено «не дольше 48 часов»).
- `server/src/telegram.ts:50-67`: initData можно повторить в течение 5 минут (нет одноразовости по `hash`).
- CORS `ADMIN_ORIGIN = https://tryserpy.github.io` — общий origin всех Pages-репозиториев владельца (приемлемо, если все они его).

## Требования, выполненные частично или не выполненные
- «5 попыток кода», «5 неверных PIN — закрыто на час» — обходятся параллельностью (п.1, п.2).
- «Резервирование до запроса и списание после» — для ученика нет резерва (п.11); брошенный запрос не списывается вовсе (п.3).
- «Разблокировка только из панели» — обход удалением аккаунта (п.5).
- «В GitHub issue без почты, ID» — ID не вычищаются (п.8).
- «PIN для опасных действий» — бюджет шагами и группы без PIN (п.9).
- «Все автоматические решения — по данным сервера» — баллы аккаунту за неподтверждённый заголовок устройства (п.4).

## Проверено и признано надёжным (предварительно)
- Ключ OpenAI: только в `Authorization` к api.openai.com; в ответах, тревогах и `console.error` (только `e.name`) не встречается. Промт собирает сервер, лишние/«промтовые» поля отклоняются (`guard/rules.ts:310-348`), «Свои указания» ≤400 знаков отдельным последним блоком.
- SQL: все запросы параметризованы; динамический `WHERE` в `gate` собирается из фиксированных шаблонов.
- Подпись: метод, путь+query, SHA-256 тела, время, nonce, id устройства; окно 2 мин; nonce в DO ученика 5 мин, проверяется после подписи; P-256 SPKI, подпись ровно 64 байта; токен доступа HMAC с назначением, привязан к устройству, аккаунту и сессии; сравнения — `safeEqual`.
- Refresh: ротация, повтор старого → закрытие всех сессий, сверка устройства и аккаунта сессии.
- Счётчики ученика и бюджета — Durable Objects (последовательно), один запрос одновременно, бюджет месяц/сутки с резервом.
- `/v1/auth/start`: одинаковый ответ для любой почты, PoW с HMAC, сроком и одноразовостью, лимиты 3/час почта и 10/час IP.
- initData: HMAC по схеме Telegram, свежесть 5 мин, id владельца; вебхук — секрет + id владельца в `from` и `chat`.
- Тревоги: маски почт и IP, без текстов задач; повторы 30 с / 2 мин / 10 мин, затем письмо.
- В базе нет текстов задач, фото, ответов ИИ; баги — 90 дней, снимок не хранится.
