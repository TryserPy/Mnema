# Архитектурный разбор: как новые функции ложатся на Мнему 1.8.0

Роль: Architecture Agent. Код проекта не менялся. Отчёты других агентов не читал.
Метки: **[выполнено]** — я запустил код и увидел результат; **[чтение]** — вывод из чтения кода; **[догадка]** — оценка без проверки.
Все «scratch»-проверки лежат в `scratchpad/arch/` (см. раздел 7), в репозиторий ничего не попало.

## 0. Главное за одну страницу

1. **Почти всё новое уже наполовину есть.** План до контрольной (`srs.ts:536-640`), «Карточки из конспекта» (`ImportantPanel.tsx:189-287`), предпросмотр и «Вернуть» для пачки правок (`changes.ts`, `ChangesDialog.tsx`), «Объясни иначе» (`ai.ts:66`, `Review.tsx:223`), меню выделения (`NoteEditor.tsx:85-96, 432`), тест с вариантами (`testgen.ts`), стихи (`poem.ts`). Нужны не параллельные подсистемы, а **три связующих слоя**: (а) единая «слабость» (`weakness.ts`), (б) «план/сессия» (`plan.ts` + запуск шагов), (в) расширение журнала (тип ошибки, ответы теста, «внеплановое» повторение).
2. **«Умный план» и «Учебный автопилот» из брифа — одна и та же функция.** Один модуль `plan.ts` (список шагов), два вида на экране: список «что в плане» и кнопка «Учиться», которая идёт по шагам. Делать две реализации нельзя.
3. **В брифе противоречие про формулы.** Строка «Справка: формулы УБРАТЬ, моды УБРАТЬ…» стоит в разделе «Справка»; в `Help.tsx:8` ровно такие вкладки: `'formulas'` и `'mods'`. Скорее всего автор просит убрать **разделы справки**, а не сами формулы. Убрать сами формулы = убрать KaTeX/редактор, а это бьёт по физике/алгебре/ОГЭ/ЕГЭ и по пунктам брифа «формулы» в «Конспект → набор» и «решить пример». Нужен один уточняющий вопрос автору (раздел 4).
4. **Три факта про данные, которые меняют план работ [выполнено]:**
   - `normalizeData` — белый список полей верхнего уровня: любое новое поле `AppData` (корзина, история) **теряется при загрузке**, пока его не добавить (`store.ts:176-188`).
   - `mergeData` берёт `...local` и знает только свои поля: новое поле с другого устройства **молча пропадает** (`sync.ts:101-104`).
   - Слияние тем целиком по `updatedAt` **уже сейчас теряет правку конспекта**: ПК правит конспект (T1), телефон позже ставит ★ на старой копии (T2 > T1) — после синхронизации конспект старый (`sync.ts:8-10, 31-54`). История версий без починки этого места — полумера.
5. **Граф лагает из-за числа узлов и рёбер, а не из-за «плохой оптимизации» [выполнено на синтетике]:** 1300 узлов / 10 400 рёбер → 8,5 мс на один шаг физики × 381 шаг до остановки (≈3,2 с процессора) только на физику, до отрисовки. Лечится моделью показа (уровни детализации, «фокус + окружение»), а не микрооптимизациями.
6. **Четыре разные «определения освоенности» в коде** (`topicMastery.learned`, `topicStatus`, «слабые темы» в `Stats.tsx`, `planFor().weak`). Если добавить пятое, интерфейс начнёт спорить сам с собой. Нужно одно ядро (`weakness.ts`) и один словарь для экрана: «выучено» (прогресс) ≠ «готовность к дате» ≠ «слабые места».

## 1. Карта «что уже есть» по каждой функции

Оценка сложности: S ≤ 1 дня, M 2–4 дня, L ≥ 1 недели **[догадка]**.

### 1.1 Умный план + автопилот (одна функция)

| Что уже есть | Где |
|---|---|
| Очередь на сегодня: повторения, обучение, новые по лимиту, перемешивание тем (interleaving) | `srs.ts:355-415` (`buildQueue`), `srs.ts:327` (`interleaveByTopic`, не экспортирован) |
| Счётчики «на сегодня» с кэшем | `srs.ts:430-454` (`todayCounts`) |
| Контрольные: новые карточки до даты, «освежить заранее» последние 2 дня | `srs.ts:551-640` (`examGroups`, `planFor`, `examBoost`, `examPlan`) |
| Предметы завтрашних уроков идут первыми; разминка 5 самых забытых | `srs.ts:398-404`, `643-666` |
| Домашка по группам (просрочено/сегодня/завтра…), напоминания | `homework.ts:37-62`, `Today.tsx` (`HomeworkToday`) |
| Стихи к повтору сегодня | `poem.ts:duePoems`, `Today.tsx:131-141` |
| Оценка времени «около N мин» | `Today.tsx:21-23` (средний `ms` последних 200 ответов) |
| Экран повторения принимает область: `topicId`, `subjectIds`, `cardIds`, `limit`, `cram`, `focus`, `mini` | `types.ts:298`, `Review.tsx:39-42` |

Чего нет: (а) нет объекта «шаг плана»; (б) нет запуска **последовательности** экранов — `Review` по окончании возвращает на тему или на «Сегодня» (`exit`, `Review.tsx:268-272`), «Дальше» нет; (в) нет повторения **не наступивших** карточек с записью в FSRS (`buildQueue` без `cram` выкидывает всё, у чего `due > end`, `srs.ts:369`; а `cram` ничего не записывает, `Review.tsx:139-146`); (г) домашка и стихи не имеют «веса», их нельзя сравнить с карточками по срочности.

**Как ложится.**
- `src/plan.ts` — чистая функция `buildPlan(data, now, {minutes?}) → PlanStep[]`. Шаг = `{id, kind, title, why, minutes, route}`, где `route` — **обычный существующий `Route`** (`review` с `cardIds/limit/subjectIds`, `test`, `topic` с вкладкой стиха). Исключение — шаг «домашка» (ручной, галочка), чтобы не превращать план в To-Do.
- Минуты → число карточек: `limit = round(minutes*60000 / медианный_ms)`; медиану вынести из `Today.tsx:21` в `srs.ts` (сейчас среднее, оно искажено долгими паузами; `ms` обрезан 5 мин, `store.ts:800`).
- Запуск «Учиться»: модуль-синглтон `session.ts` (**не в `AppData`**, как `scheduleNotifications`): `{steps, i}`. `Review`/`TestScreen` на экране итогов вместо «На главную» спрашивают `session.next()` и показывают «Дальше: …». В `Route.review` добавить необязательное `step?: {i, n, title}` (только для надписи «Шаг 2 из 4»). Если приложение перезапустили посреди плана — план просто пересчитывается, выполненные шаги исчезают сами (карточки уже повторены) — идемпотентно, ничего хранить не надо.
- Хранить в `Settings` (на устройстве, не синхронизируется): `plan?: {minutes: number}` — «сколько минут в день».
- `Route`: добавить `{name:'plan'}` только если нужен отдельный экран «что в плане»; кнопка «Учиться» на `Today` может обойтись без нового маршрута.
- Android: кнопка «Назад» уже закрывает `review` через Esc (`App.tsx:310-335`); для сессии достаточно, чтобы «Назад» из `review` вёл на `today` и сбрасывал `session`.

Сложность M–L. Зависит от: `weakness.ts` (1.2/раздел 3), режима «внеплановое» (раздел 3.4). Главный риск: `Review.tsx` — «горячий файл» (план, объяснение ошибок, внеплановое повторение — всё туда), см. раздел 5.

### 1.2 Подготовка к контрольной

Уже есть: `Topic.examDate` (`types.ts:96`), группировка «тема + подтемы» с отсевом пересечений (`taken`, `srs.ts:551-567`), прогноз `recallAfter` (`srs.ts:539`), число новых на день `perDay`, «слабых к дате» `weak` (r < 0,9) (`srs.ts:582-626`), блок «Контрольные» на `Today` и `ExamPlanLine` (`Today.tsx:154-193, 452-480`), «Проверить себя» (тест), пробный тест `testgen.ts`, подсказка за 0–2 дня (`tips.ts`).

Чего нет: (а) процент «готовности» — сейчас везде показывается «выучено N%» = доля элементов в состоянии Review со стабильностью ≥ 3 дней (`srs.ts:484-497`), это не готовность на дату; (б) список конкретных слабых карточек и кнопка «Исправить»; (в) **ошибки теста не пишутся нигде**: `TestResult` хранит только `{total, correct}` (`types.ts:151-157`, `TestScreen.tsx:48`), «Повторить ошибки» идёт через `cram` — без записи в FSRS (`TestScreen.tsx:181`); (г) распределение **повторений** по дням до даты (есть только распределение новых).

**Как ложится.** Отдельной сущности «Контрольная» заводить не надо: `examDate` на теме + `topicSubtree` уже покрывают «контрольная по главе» (родитель + подтемы). Новый чистый модуль `examPrep(data, topicId, now)` поверх `weakness.ts`: `{readiness (0..1 на дату), perDay[], weakItems[], reasons[]}`. «Готовность» = средняя вероятность вспомнить **на дату контрольной** `recallAfter((дата − last_review)/DAY, stability)`; несыгранные элементы считаются нулём. Это та же формула, что уже в `planFor` (`srs.ts:609`), поэтому число объяснимо («к дате ты вспомнишь ≈43%»). Кнопка «Исправить» → `Route.review {cardIds, ahead: true}` (новый флаг, раздел 3.4). Одна дата на тему — достаточно; «несколько несвязанных тем на одну контрольную» решается датой на каждой теме (уже работает).

Сложность M. Зависит от: `weakness.ts`, флаг `ahead`, запись ответов теста (раздел 3). Риск: слово «процент» — в интерфейсе уже три разных процента; назвать «готовность» и больше нигде этот термин не использовать.

### 1.3 Конспект → учебный набор одной кнопкой

Уже есть три готовых куска, параллельного строить не надо:
- **Без ИИ (всегда доступно):** `findImportant(note, settings)` находит жирное, определения, даты, имена, курсив, рамки (`important.ts:168-223`); `cardDraft(item)` строит черновик карточки (`important.ts:226-250`); `BulkCards`/`NoteToCards` — окно с галочками (`ImportantPanel.tsx:189-287`); кнопка «Карточки из конспекта» в меню темы (`TopicScreen.tsx:167`) и «Сделать из конспекта» (`TopicScreen.tsx:557-583`).
- **С ИИ:** `ChangesDialog` уже умеет «разобрать текст → предпросмотр → применить → Вернуть» (`ChangesDialog.tsx:24-62`; `parseChangeFile`, `planChanges`, `revertChanges` в `changes.ts`); инструкция для нейросети с названиями уже существующих тем — `aiInstructions` (`changes.ts:761`) и `MNEMA_TEXT_GUIDE` (`mnemaText.ts`). Сегодня это путь «скопировал → вставил в чужой чат → вернул файл». Внутри приложения ИИ вызывается напрямую: `window.mnemaApi.aiAsk(req)` одинаково на Windows и Android (`electron/ai.cjs`, `platform/android.ts:121`, общее ядро `shared/aiCore.mjs`).
- **Куда положить результат:** списки `StudyList` (`terms`, `dates`, `vocab`) уже существуют; строки списка сами становятся карточками (`store.ts:643-654`).

**Как ложится.** Кнопка «Сделать набор» = два пути за одним окном:
1. Без ИИ: расширить `BulkCards` — найденное разносится по **типам результата**, а не только в карточки: определения «X — это…» → строка списка «Термины» (в бэклоге уже записано: `PROJECT.md` §14, пункт 3), даты → список «Даты», жирное → «пропуск», вопросы/задания — только с ИИ.
2. С ИИ (`features.ai` включён): `aiAsk({system: aiInstructions(...), text: конспект без картинок (hideImages, changes.ts:162)})` → ответ в формате Мнема-текст → `openChanges(text)` (уже принимает текст, `ChangesDialog.tsx:19`) — пользователь видит предпросмотр и «Вернуть», нейросеть **ничего не удаляет** (правило уже в контексте проекта). Ограничения: `maxTokens` зажимается до 6000 (`aiCore.mjs:184`), стриминга нет (один ответ) → для длинных конспектов резать на части по заголовкам `##`.
3. «Формулы» в наборе: либо как список `formulas` (вид списка есть), либо не делать, если формулы убирают (раздел 4).

Сложность S–M (без ИИ) + M (с ИИ). Зависимость: только `ai.ts` + `ChangesDialog`. Риск: ИИ «придумывает» факты — в окне предпросмотра уже есть место для пометки «проверь по учебнику» (как в `Review.tsx:476`).

Задание — это **способ показать уже существующие карточки**, значит модуль `src/drills.ts` (чистый): `makeDrill(kind, data, topicId, rnd) → {items, check(answer) → {ok, perCard, err?}}`.

Это нужно решить с автором/исследователями; для архитектуры важна развилка, а не ответ.

Сложность M (каркас + 3–4 вида), далее по одному виду S. Зависит от расширения журнала.

### 1.5 Объяснение ошибок («Неверно. Почему?» → объяснение → похожий вопрос → «Объяснить проще»)

Уже есть: кнопка «✦ Объясни иначе» (подсвечивается после ≥2 «Снова» на карточке) и блок ответа ИИ (`Review.tsx:460-500`), `explainDifferently` (`ai.ts:66-86`), `typedOk` для ввода/числа (`Review.tsx:91`), выравнивание слов «ожидалось / сказано» с отметками `ok/miss/wrong` (`poem.ts:compareRecital`, пригодится для показа «где расходится»), задача с новыми числами как готовый «похожий вопрос» (`instantiate(seed)`).

Чего нет: введённый неверный ответ **никуда не передаётся и не сохраняется** — ИИ получает вопрос/ответ карточки, но не то, что написал ученик (`ai.ts:66`); нет типа ошибки; нет «простого» режима.

**Как ложится (три уровня, каждый работает без нижестоящего):**
- **L0, без ИИ:** показать эталон, `card.why`, **предложение из конспекта**, где встречается ответ (`sentences()` + `findTextRange`), расхождение введённого с эталоном (`compareRecital`/`checkTyped`). Это уже «объяснение по материалам ученика».
- **L1, ИИ:** `explainMistake({question, expected, given, why, noteSnippet, simpler})` в `ai.ts` рядом с `explainDifferently`; «Объяснить проще» — тот же вызов с `simpler: true` и предыдущим текстом. Промпты — чистые функции (тестируются без сети).
- **«Похожий вопрос»:** `problem` → новое зерно (`instantiate`); словарные/терминные строки → «путаница»: карточка, чей ответ ученик ввёл/выбрал (в бэклоге: «Путаю эти два», `PROJECT.md` §14); с ИИ — новая формулировка как черновик карточки через `planChanges`.
- UI: в `Review.tsx` внутри блока ответа, свёрнуто («Почему неверно?»), разворачивается само только когда `typedOk === false`.
- Сохранять **тип ошибки** в журнал (раздел 3).

Сложность M. Зависит от: журнала. Риск: конфликт правок в `Review.tsx`.

### 1.6 ИИ внутри конспекта при выделении

Уже есть: единый механизм действий над выделением `SelAction` (`NoteEditor.tsx:85`), пункты для меню Android `SEL_MENU` — JS присылает список, Java строит меню динамически, до 12 пунктов (`NoteEditor.tsx:88-96`, `MnemaWebView.java:22-43`) → **Java менять не надо**; панель выделения на компьютере по правой кнопке (`NoteEditor.tsx:703-714`), кнопка «Выделенное» на телефоне (`NoteEditor.tsx:486-500`), `onMakeCard(text)` для «В карточку».

**Как ложится.** Добавить **один** пункт `ai` («ИИ…») к `SelAction`/`SEL_MENU`/панели; он открывает небольшое окно с 2 крупными кнопками («Объяснить проще», «Пример») и «⋯» (как для 5 класса, вопрос по тексту, своё). Результат показывается в окне, в конспект **не пишется сам**: кнопки «В карточку» (`onMakeCard`), «Вставить рамкой» (цитата-блок уже есть), «Объяснить ещё проще». Перед вставкой — снимок версии (раздел 2). В запрос отдавать выделение + абзац вокруг + названия предмета/темы; картинки вырезать (`hideImages`). Видимость: только при `features.ai` (`aiAvailable`, `ai.ts:5`) — принцип «выключенное не видно» соблюдён автоматически. Промпты — чистые функции `aiPrompt(kind, ctx)`.

Сложность M. Зависит от: ничего, кроме `ai.ts`. Ограничения: нет стриминга и ограничение 6000 токенов (`aiCore.mjs:184`); на бесплатных моделях частые 429 (уже есть `humanError`, `ai.ts:25-48`). ### 2.3 История версий конспекта

**Что нельзя класть в историю как есть.** Конспекты содержат встроенные картинки (`data:` в Markdown — рисунки, вырезки из учебника). Копия текста с картинками ×N версий взорвёт файл. Уже есть решение для подмены: `hideImages`/`imageToken` (`changes.ts:152-162`) — но хэш там 32-битный, для хранилища использовать более длинный (или SHA-256 через `crypto.subtle`).

**Предлагаемая стратегия (параметры — предложение, подбирать на данных):**
- Хранить снимок **только текста**, картинки заменены токенами; сами картинки — в общем словаре `noteImages` (один экземпляр на одинаковую картинку), чистить по счётчику ссылок при удалении версий.
- Снимать **предыдущий** текст в границах правки, а не на каждую букву: при уходе из темы / сворачивании / паузе ≥ 10 мин; обязательно **перед** массовой заменой — «ИИ-вставка», «Файл изменений» (`noteMode: replace`, `changes.ts:395`), «Из учебника», слияние при синхронизации, «Восстановить».
- Не снимать, если текст отличается < 40 знаков или конспект < 80 знаков.
- Лимиты: ≤ 25 версий на тему; общий потолок ≈ 3 МБ текста + ≈ 6 МБ картинок; прореживание: последние 10 подряд, затем по 1 в день за 2 недели, затем по 1 в неделю за 3 месяца.
- Сжатие: три новейшие версии целиком, более старые — `deflate` (`fflate` уже в зависимостях) → base64, флаг `z:1`. Дельты не нужны: Markdown сжимается в разы **[догадка: на синтетическом тексте 5076 Б → 378 Б base64; реальные конспекты будут хуже]**, а своя дельта-логика — лишний риск.
- **Где хранить:** в `AppData` как локальное поле (не в облаке и не в Wi-Fi-обмене). Вырезать при отправке в трёх местах: `cloud.ts:115`, `SyncDialog.tsx:44` и ответ `acceptIncoming` (`SyncDialog.tsx:62-66`) — одной функцией `forSync(data)`. Альтернатива (IndexedDB) отпадает: не попадает в ежедневные копии и «Сохранить копию», на Android проверять не на чем (WebView грузит `https://HOST/…`, DOM storage включён, `AppActivity.java:53,194`, но в данных-файле команда сознательно выбрала мост).
- В копию «Сохранить копию» (`Settings.tsx:424`, `exportJson`, `store.ts:887`) история попадает — это страховка; потолок размера её ограничивает.

**Починить заодно (иначе история бессмысленна):** слияние конспекта.
- `Topic.noteAt` + правило в `mergeData`: `note` берётся от стороны с более новым `noteAt`, остальные поля — от более новой `updatedAt`. Проигравший текст при слиянии кладётся в историю как `before-sync` (функция `mergeData` чистая и уже имеет `local`; результат можно обогатить, тест — как в `sync.test.ts`). Подтверждено выполнением: сейчас проигравшая сторона теряет текст полностью (`arch/vt/lww.test.ts`).
- «Фантомные правки»: `NoteEditor` при закрытии всегда отдаёт `getMarkdown()` (`NoteEditor.tsx:253-262`), а `TopicScreen` сравнивает `md !== topic.note` (`TopicScreen.tsx:420`): любое отличие нормализации редактора от сохранённого текста перезаписывает конспект и сдвигает `updatedAt` при простом открытии **[чтение]**. Снимки и `noteAt` должны срабатывать от настоящей правки (`onUpdate` с `docChanged`), а не от «текст в сторе изменился».

### 2.4 Корзина против `deleted` и `restoreRemoved`

Что есть: `deleted` — только **метки** «что и когда удалено» для слияния (`store.ts:330-336`); `Removed` — снимок содержимого, живущий **в замыкании тоста «Вернуть»** (`store.ts:339-379`, `SubjectDialogs.tsx:221-225`): исчезает вместе с тостом (8 с) и при перезапуске. Покрытие неполное: у `deleteCard` (`store.ts:750`), `deleteHomework`, `deleteList`, `deleteFolder` содержимое не сохраняется; `changes.ts` ставит метки напрямую (`changes.ts:263,275`), а «Вернуть» там — отдельная диффовая логика (`revertChanges`).

**Предложение.**
- **Не мягкое удаление** (флаг `deletedAt` в `Topic/Card/…`): его пришлось бы учитывать во всех `data.topics.filter(...)` приложения (граф, поиск, статистика, очередь, виджеты…) — высокий риск регрессий. Нужен **отдельный контейнер** `trash`, остальной код не знает о его существовании.
- Метки `deleted` остаются как есть; корзина хранит только содержимое: `TrashItem = {id, at, kind, title, counts, payload: Removed-без-журнала, marks}`. Журнал (`logs`) в корзину **не класть**: тема на 50 карточек × 20 ответов = ≈1000 записей ≈ 227 КБ **[оценка]**; прогресс (`states`) сохраняется, история ответов — нет (в статистике удалённое и так исчезает).
- Единая точка захвата: `captureDeleted(before, after)` — чистая функция; вызывать в `commit()` только когда `next.deleted !== data.deleted` (ссылочная проверка — на горячем пути почти бесплатно). Она по новым меткам находит объекты в `before` и кладёт в корзину. Так покрываются **все** пути удаления без правки каждой функции: `deleteSubject/Topic/Many/Card`, применение «Файла изменений», слияние, где удалённое пришло с другого устройства (пометить `by:'sync'`).
- Восстановление = существующая `restoreRemoved` (`store.ts:362`): она уже снимает метки и ставит `updatedAt` новее метки — поэтому после следующей синхронизации восстановленное не удалится снова. Расширить `Removed` необязательными `folders`, `homework`. После «Вернуть» из тоста удалять соответствующий элемент корзины (по `marks`), иначе дубль.
- Срок и размер: 30 дней (метки живут 180) и ≤ 5 МБ; больше — предупреждение при удалении («слишком большое для корзины: удалить насовсем?»). Очистка при запуске.

### 3.2 Чего не хватает

1. **Тип ошибки** — нигде. Минимальный набор, который можно получить без ИИ: `blank` (не знал: пусто/«не помню»), `near` (почти: опечатка, расстояние ≤ 2 — в `poem.ts` уже есть `lev`, приватный), `mix` (ввёл/выбрал ответ **другой** карточки — в тесте дистрактор знает, чья он, `testgen.ts:56-70`; для ввода — поиск среди ответов темы), `slow` (верно, но `ms` > 2× медианы — выводится без хранения), `overconf` (уверенность 2 + «Снова» — выводится, если включена).
2. **Ошибки теста** по вопросам (`TestResult` = только итоги).
3. **Внеплановые/cram-повторения** не записываются вовсе (`Review.tsx:139-146`).
4. **Стихи** не в журнале; **домашка** не имеет результата.
5. Нет поля «откуда ответ» (повторение/тест/задание/внеплановое).

Дедупликация журнала `key|at` не мешает: записи с `src` просто несут больше полей.

### 3.3 Формула (предложение, веса не калиброваны **[догадка]**)

Для элемента на момент `t`: `R` = `recallAfter((t − last_review)/DAY, stability)`; `L` = `min(1, lapses/leechThreshold)`; `D` = `(difficulty−1)/9`; `F` = доля «Снова» среди последних 3 записей элемента; `slow` по медиане `ms` самого ученика.
`weak = 0,45·(1−R) + 0,20·L + 0,15·D + 0,15·F + 0,05·slow`; причины («забыл 3 раза», «не повторял 21 день», «ошибся уверенно», «перепутал с X») — **текстом**, чтобы слабость была объяснимой, а не числом. Для `reps < 2` — отдельное состояние «мало данных», а не «слабо». FSRS-`R` — уже откалиброванный вероятностный прогноз, остальное — эвристика; проверить можно «обратным прогоном» на журнале самого автора (предсказывает ли `weak` следующее «Снова»).
Тема: «готовность на дату d» = среднее `R(d)` по элементам (несыгранные = 0); «слабые места» = верхние N элементов по `weak`; «Исправить» = их `cardId`.

Реализация: `src/weakness.ts` — чистые функции + тесты, читает только то, что уже есть; кэшировать по ссылке на `data.logs/states/cards` как `todayCounts` (`srs.ts:417-441`), потому что перебор журнала — O(L).

### 3.4 Что поменять в журнале и экране повторения

- `ReviewLogEntry`: необязательные `src`, `err`, `mix` (см. 2.2). **Новые виды записей нельзя лить в `logs` без пометки**: этот массив читают как «настоящие повторения» ≥ 10 мест — `newIntroducedToday` по `prevState===0` (`srs.ts:309`), `seenCards` в очереди (`srs.ts:386`), `streak`, `weekSummary`, `achievements`, KPI «запоминание» в `Stats.tsx:157`, средняя длительность в `Today.tsx:21`, `removeCards`, `restoreRemoved`, слияние. Поэтому: **настоящие повторения (включая внеплановые, они меняют FSRS) — в `logs` с `src`**, **узнавание/задания — в `tests`** с `kind`/`answers`. Существующие потребители остаются нетронутыми.
- `Route.review` + необязательное `ahead?: boolean`: очередь из **ненаступивших**, но слабых карточек (`R < порога`), ответы пишутся в FSRS как обычно (`ts-fsrs` умеет ранние повторения; влияет на интервал мягче). Развилка для решения автора: считать ли «Исправить» обычным повторением (рекомендую — иначе слабость не уходит) или «без изменения расписания» (как `cram`). Сейчас оба пути, которыми приложение возвращает к ошибкам («Повторить ошибки» в тесте, разминка), **не пишут ничего**.
- `recordReview(p)` (`store.ts:776`) расширить необязательными `src`, `err`, `mix`.

### 5.1 Главные риски

1. **Потеря правки конспекта при синхронизации** — уже есть сегодня **[выполнено]**; история версий без `noteAt` и `before-sync` лишь запишет постфактум, что потеряно не будет только при снимках.

6. **Семантика FSRS для «внеплановых»** (раздел 3.4) — решение до реализации.
7. **ИИ:** нет стриминга, потолок 6000 токенов, бесплатные модели упираются в 429; все ИИ-функции обязаны работать без ИИ хотя бы на уровне L0 (принцип «офлайн-приложение»); отправка текста конспекта стороннему сервису — оставить явный текст в «Возможностях/ИИ».
8. **Граф:** цифры из синтетики; на телефоне не проверялось.
9. **Стихи в `Topic`:** при конфликте двух устройств проигрывает вся тема, включая `history/lineMiss/review`.

## 6. Что подтверждено, а что нет

**Выполнено (воспроизводимо):**
- слияние теряет правку конспекта при «более позднем» `updatedAt` на старой копии; новые поля верхнего уровня при слиянии пропадают — `arch/vt/lww.test.ts`;
- `normalizeData` теряет неизвестные верхние поля, но сохраняет неизвестные поля тем/журнала/настроек — `arch/vt/norm.test.ts`;
- `marked` без математического токенизатора портит LaTeX — `arch/marked-math.mjs`;
- время шага d3-физики и размер графа на синтетических данных — `arch/vt/graph.test.ts`;
- размеры записей и сборки — `arch/sizes.mjs`, `ls`/`du` по `dist/` и `node_modules`.

**Прочитано, не запускалось:** все ссылки `файл:строка` кроме перечисленного; причины багов 2 и 3; цепочка ИИ на Android; поведение меню выделения Android.

**Предположения:** веса «слабости»; степень сжатия реальных конспектов; ×3–5 для телефона в графе; безопасность отказа от `woff/ttf`; порядок сложности S/M/L; что сериализатор TipTap портит `$…$` без расширения.
